# MySQL import feasibility spike

Status: parser and isolation evidence for #350; the execution boundary is still under construction. No dump in this corpus is authorized for execution against a PV-managed track yet.

The initial `mysql-dump` domain crate now frames SQL and `DELIMITER` directives by byte range with bounded memory, extracts parser-verified source database spans for supported routing statements, and streams verified byte patches. Its callback must reject any `SET` that changes the SQL lexer before scanning the next statement. The crate does not yet classify all SQL effects, transform a complete dump, or launch a client.

## Reproduce the corpus

`sh it/fixtures/mysql-import/generate.sh` starts disposable MySQL 8.0.46, 8.4.9, and 9.7.0 containers matching PV's current tracks. Each produces a plain single-database dump, multi-database dump, `--add-drop-database` dump, `--no-create-db` dump, and `--all-databases --no-data` dump. The source includes two ordinary user databases, a quoted mixed-case name, a qualified cross-database view and trigger, a procedure with static SQL, a procedure using dynamic `PREPARE`, a disabled event, non-ASCII text, and hex-encoded blob data. The smaller `--all-databases` fixtures retain actual system-schema DDL but omit system account data. Hand-written phpMyAdmin-style and hostile scripts supplement generated syntax.

The generator uses a known fixture-only root password in disposable containers. Production import credentials must use owner-only storage and must not appear in argv or logs.

## Parser comparison

The comparison ran Rust 1.98.1 in a Docker container against the unmodified 8.4.9 multi-database dump. The standalone `it/fixtures/mysql-import/parser-probe` harness pins `sqlparser` 0.63.0, `qusql-parse` 0.11.0, `sqlglot-rust` 0.10.30, and `squonk` 3.0.0. It configures QuSQL with its MariaDB dialect. Run it with `--samples` for representative statements, a dump path for whole-file behavior, or `--chunks <dump>` for the provisional delimiter-split results. These are syntax results, not evidence that a parser has classified SQL effects or made a dump safe.

```sh
docker run --rm -v "$PWD:/work" -w /work/it/fixtures/mysql-import/parser-probe rust:1.98 sh -c 'cargo build --release --locked && target/release/pv350-parser-probe --samples && target/release/pv350-parser-probe --chunks ../8.4.9/databases.sql'
docker run --rm -v "$PWD:/work" -w /work python:3.13-slim python it/fixtures/mysql-import/parser-probe/benchmark.py it/fixtures/mysql-import/parser-probe/target/release/pv350-parser-probe 64
```

| Candidate | Full generated dump | Representative statements |
| --- | --- | --- |
| `sqlparser` | Stops at generated `CREATE DATABASE ... DEFAULT ENCRYPTION`. | Parses table, view, and trigger, including the trigger inside executable comments with source spans. Rejects the procedure's `BEGIN` body and `CREATE EVENT`. |
| `qusql-parse` | Reports unsupported `USE` and dynamic `PREPARE`; returns some statements even when issues exist. | Parses database, table, and view. Reports errors for trigger/procedure, rejects event and `USE`, and returns zero statements without an error for the executable-comment trigger. |
| `sqlglot-rust` | Stops in the executable-comment session preamble. | Parses database, `USE`, table, view, and event. Rejects compound trigger/procedure bodies and the executable-comment trigger. |
| `squonk` | Stops at generated `CREATE DATABASE ... DEFAULT ...` options. | Parses `USE`, table, view, compound trigger/procedure, event, and the executable-comment trigger into an AST with byte spans. |

A **spike-only** line-end delimiter splitter fed each chunk of the current generated dumps to `squonk`. All three supported tracks produce the same counts for the multi-database fixture: 145 accepted AST statements and 12 rejects. On 8.4.9, the plain fixture yields 80/3 accepted/rejected, `--no-create-db` yields 145/9, `--add-drop-database` yields 148/12, and `--all-databases --no-data` yields 286/33. The rejects in the multi-database fixture are three `CREATE DATABASE` option lists, eight `ALTER TABLE ... DISABLE/ENABLE KEYS` statements, and one `CREATE FUNCTION` body using `SELECT ... INTO`. The splitter is intentionally not production code: it does not prove correct boundaries when a delimiter appears inside a string or comment, nor bounded memory for large extended inserts.

The `squonk` executable-comment AST retains a trigger with its definer, body, qualified `analytics.audit` reference, and byte spans into the original statement. A focused test confirms that identifier spans point to exact bytes inside executable comments, including backtick-quoted database names. This makes selective source-span patches plausible. The production reader must still verify every patched span and preserve all other bytes. A successful AST parse is insufficient: PV must positively classify statement effects, dynamic SQL, client commands, and every qualified reference.

Both the phpMyAdmin fixture and its CRLF copy parse as nine statements with `squonk` and `sqlparser`; `sqlglot-rust` stops at `START TRANSACTION`. The hostile full-file probe fails at the earlier `SELECT ... INTO OUTFILE`, before reaching its client shell command; direct client-command rejection remains untested. This is parser failure behavior, not proof that every earlier hostile statement would be classified safely if split. The `--all-databases` fixtures contain actual `mysql` system-schema DDL but no `sys`, `performance_schema`, or `information_schema` sections; `system-sections.sql` supplies those explicit skip cases for later policy tests.

The regenerated corpus adds a stored function with `SELECT COUNT(*) INTO` and a non-ASCII table identifier. The 8.4 multi-database dump now produces 145 accepted AST statements and 12 rejected chunks. The new function is one of the rejects: `squonk` expects a compound-body terminator at `INTO`; all three other candidates also reject that generated function. Support for arbitrary stored functions cannot be claimed from the original procedure sample. A first release may accept parsed function forms but must reject unsupported bodies during preflight with a location, unless the parser is extended upstream or a safe alternate representation is proven.

`parser-probe/benchmark.py` generated a single-row `INSERT` with a 16 MiB hex literal. The probe's `read_to_string` plus `squonk` parse path took 0.02 seconds and reached 36,792 KiB peak RSS in a Python 3.13 Docker container. A 64 MiB literal took 0.06 seconds and reached 135,096 KiB peak RSS. These measurements are Linux arm64, Rust 1.98.1 release build, with input creation outside the measured child process. This probe path's memory scales with statement size; it fails the issue's bounded-memory requirement for arbitrarily large inserts. A production reader must stream ordinary extended `INSERT` values after validating their grammar and target, or set a documented input ceiling. The latter would fall short of #350 as written.

The `squonk` 3.0.0 package and `squonk-ast` are MIT licensed. Their manifests deny unsafe code, and `squonk-ast` forbids it. The MySQL-only dependency tree has just two transitive runtime packages, `squonk-ast` and `thin-vec`. In an ad hoc isolated Rust 1.98.1 Linux arm64 release build, a stripped baseline binary was 332,504 bytes and an otherwise equivalent binary calling `squonk::parse_with` was 4,395,736 bytes, a 4,063,232-byte increase. This is a small binary-size probe, not a measurement of PV's final linked executable. `squonk` is also a new parser with demonstrated MySQL gaps, so pinning and fixture regression tests are needed if adopted.

## Isolation probe

In disposable MySQL 8.0.46, 8.4.9, and 9.7.0, a login account granted privileges only on `project_admin.*` could not create a table in `unrelated_project`, create another database, change a global setting, or create an object with `root@localhost` as its definer. With binary logging disabled, it created a view, row trigger, procedure, and stored function with an explicit self-definer in its target. After `ALTER USER ... ACCOUNT LOCK`, the account could no longer log in, while all four definer-backed objects still worked. This demonstrates that a restricted owner account can preserve imported stored objects after explicit source `DEFINER` values have been normalized. The rewrite itself and the account, grants, lock, and cleanup lifecycle need production tests.

With default binary logging, creating the trigger as this restricted account failed with MySQL error 1419 demanding `SUPER` or `log_bin_trust_function_creators`. PV previously did not set a binary logging option, and the tested MySQL Docker tracks enable it by default. The user approved disabling it for PV's local development tracks so triggers and functions can be imported without granting dump SQL server-wide privilege. The runtime now passes `--skip-log-bin`.

## Decision and remaining proof

Choose the issue's outcome **1: an existing parser plus a minimal PV dump reader**, with `squonk` as the leading candidate. Its MySQL AST covers the sampled procedures, trigger, event, and executable comments while retaining byte spans; the generated function using `SELECT ... INTO` remains unsupported. A PostgreSQL/MySQL universal parser is not needed. The PV reader must frame `DELIMITER`, comments, quoted strings and identifiers, and large `INSERT` values; classify and transform the few known generated statements `squonk` does not parse; reject unknown syntax; and avoid buffering whole large inserts. This recommendation is provisional until complete preflight and end-to-end restored-byte tests pass.

The implementation must prove that complete preflight produces a credential-free plan and transformed file before any `mysql` client starts. It must remap `CREATE/ALTER DATABASE`, `USE`, and database-qualified references; neutralize database-level drops; skip complete system-schema sections; normalize source `DEFINER` values; reject dynamic SQL and server-scoped effects; and enforce target-only privileges during execution. Tests must cover exact-span patching, collisions, special schemas, unrecognized syntax, client commands, cancellation, nonempty targets, partial-import reporting, and later adoption of undeclared databases. A matching real-artifact macOS lane remains necessary after the Docker phase.
